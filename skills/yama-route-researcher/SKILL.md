# 山のルート調査（日本版）

日本の山について、複数の情報源を横断してルート調査レポート（Markdown）を作るスキル。
[claude-mountaineering-skills](https://github.com/dreamiurg/claude-mountaineering-skills) の `route-researcher` を、日本の山・日本の情報源・日本の登山の慣習に合わせて作り直したもの。

**情報源:** 国土地理院（地名検索・標高・逆ジオコーダ・地理院地図）、気象庁（府県天気予報・警報注意報・火山情報）、Open-Meteo（山頂標高の数値予報）、OpenStreetMap（病院・警察・山小屋・キャンプ場）、ヤマレコ、YAMAP、山と溪谷オンライン、山小屋や自治体の公式情報など。レポートの質はその山がどれだけ記録されているかに左右される。

`{skill_dir}` はこの SKILL.md があるディレクトリ。プラグインとして入れた場合は `${CLAUDE_PLUGIN_ROOT}/skills/yama-route-researcher`。

## いつ使うか

- 「槍ヶ岳を調べて」「来月、甲斐駒ヶ岳に黒戸尾根から行きたい」「八ヶ岳の赤岳、今週末の状況は？」
- 日本の山のルート情報・コースタイム・現在の状況・登山計画の相談
- 海外の山（北米など）は元プロジェクトの `route-researcher` の方が向いている

## ワークフロー

### フェーズ1: 山の特定

日本は同名の山がとても多い（駒ヶ岳、丸山、愛宕山、富士の名を持つ山など）。必ず候補を示して確認する。

1. ユーザーの発言から山名・ピーク名・ルート名（「黒戸尾根」「北鎌尾根」など）・山域（「北アルプス」「八ヶ岳」）・県名を拾う。
2. 候補を検索する:

   ```bash
   cd "{skill_dir}/tools" && uv run python find_peak.py "{山名}" [--prefecture "{都道府県}"]
   ```

   OpenStreetMap の山頂（natural=peak/volcano）と国土地理院の地名検索を突き合わせ、表記ゆれ（ヶ/ケ/が、岳/嶽 など）も試す。各候補に都道府県・市町村・標高・地図リンク（地理院地図など）が付く。
3. 候補の扱い:
   - **複数ある:** AskUserQuestion で選んでもらう。各選択肢は「{山名}（{標高}m、{都道府県}{市町村}）- {地理院地図リンク}」。山域名でほぼ確定できる場合でも、確認は省かない。「その他」も入れる。
   - **1つだけ:** 「{山名}（{標高}m、{都道府県}）で合っていますか？ {地理院地図リンク}」と確認する。
   - **見つからない:** 「山」「岳」の付け外し、別名・旧称（御岳山／御嶽山、大山（だいせん／おおやま））、ピーク名（「穂高岳」→「奥穂高岳」）、ひらがな表記で再検索。スクリプトが失敗した場合は `WebSearch "{山名} 標高 site:ja.wikipedia.org"` や `site:yamareco.com/modules/yamainfo` で座標を探す。それでも無理ならユーザーに地図リンクや別名を聞く。
4. 決まった山の名前・座標・標高・都道府県を以降で使う。

### フェーズ2: 基本情報

コンディション取得には座標が要るので、フェーズ3の前に済ませる。並列で次を調べる。

- `WebSearch "{山名} site:ja.wikipedia.org"` → 標高（三角点・最高点）、山域、山系、百名山・二百名山・三百名山・花の百名山などの区分、火山かどうか、国立公園
- `WebSearch "{山名} site:yamareco.com/modules/yamainfo"` → ヤマレコの山データ（主な登山口、登山ルート、近くの山小屋）
- 主な登山口とその座標（分かれば）、一般的なルートの往復距離・累積標高差・コースタイム

標高は国土地理院の公表値（Wikipedia・ヤマレコに載っていることが多い）を正とし、`find_peak.py` の値と大きく違えばそちらを採用する。

### フェーズ3: 情報収集

**フェーズ3A とフェーズ3B は同じ応答の中で並列に起動する。**

#### 3A: コンディション取得スクリプト

```bash
cd "{skill_dir}/tools" && uv run python fetch_conditions.py \
  --coordinates "{緯度},{経度}" \
  --elevation {標高m} \
  --peak-name "{山名}" \
  --date {山行予定日 YYYY-MM-DD（不明なら省略=今日）} \
  --trailhead "{登山口の緯度},{経度}" \
  --distance-km {往復km} --up-m {累積登りm} --down-m {累積下りm} \
  --start-time "{出発 HH:MM}" \
  --waypoint "{緯度},{経度}" --waypoint "{緯度},{経度}"
```

`--coordinates`・`--elevation`・`--peak-name` 以外は任意。距離・標高差・出発時刻は 3B の結果で分かってから再実行してよい。

返ってくる JSON:

- **location**: 都道府県・市町村、気象庁の府県予報区（office）・一次細分区域（class10）・市町村区域（class20）のコード
- **weather**: 7日間の山頂標高での予報（℃、mm、m/s）。日ごとに `freezing_level_m`（0℃高度）、`snow_line_note`、`near_summit`（0℃高度が山頂から600m以内）、`upper_wind_max_ms`（山頂付近の気圧面の風）、`wind_alert`（10/15/20 m/s の目安）、`feels_like_min_c`（風速1m/sで1℃下がる経験則による体感最低気温）
- **jma_forecast**: 気象庁の府県天気予報（平地向け）の天気文・風・降水確率と公式ページ URL
- **jma_warnings**: 対象市町村で発表中の警報・注意報（2026-05-28 からの新体系のレベル付き名称）、`mountain_relevant`、データ鮮度の警告 `stale_warning`
- **air_quality**: PM2.5 日平均（環境省の暫定指針 70μg/m³ で判定）と黄砂（dust）
- **daylight**: 天文薄明〜日の出〜日の入り〜天文薄明の時刻表（Asia/Tokyo）
- **volcano**: 山頂から15km以内の火山（OSM）と気象庁の火山情報リンク
- **municipalities**: 登山口→山頂で通る市町村
- **protected_areas**: 国立公園・国定公園など
- **nearest_hospital / police / huts / campgrounds**: 病院・警察・山小屋・避難小屋・キャンプ場（OSM、距離 km）
- **time_estimates**（距離と登りを渡したとき）: 速い／標準／ゆっくりの歩行時間、山本正嘉の**コース定数**とその目安、`--body-kg` を渡すとエネルギー消費量と脱水量の目安
- **itinerary**（さらに出発時刻を渡したとき）: 山頂到着・下山時刻、日没から逆算した引き返し時刻、`late_arrival`（目標時刻 15:00 を過ぎる）、`after_dark`（日没後になる）
- **bearings**（通過点2つ以上）: 区間ごとの方位（真北）と距離
- **gaps**: 取れなかったデータ

#### 3B: リサーチ担当エージェント（3体を並列で）

3つの Task 呼び出しを1つの応答にまとめて送る。どのエージェントも、**URL を推測して WebFetch しない**こと。まず `site:` 検索で実在する URL を集めてから取得する。WebFetch が失敗したら `uv run python {skill_dir}/tools/cloudscrape.py "{url}"`、それでも駄目なら `--render` を付ける。

#### 3C: 統合

スクリプトとエージェントの結果を1つにまとめる。どれかが失敗しても残りで続け、失敗は `gaps` に入れる。最低限「コンディション」と「ルート情報1件」があれば先に進む。

#### 3D: アクセス・規制・登山届（その場で調べる）

「自分で確認してください」で終わらせず、**実際に調べて、日付と出典つきで書く**。

1. **登山届**: 条例で提出が義務の山域がある（例: 長野県の指定登山道、岐阜県の北アルプス・焼岳・御嶽山、群馬県の谷川岳、富山県の剱岳の冬期、新潟県・山梨県・静岡県などの一部）。`WebSearch "{都道府県} 登山届 条例 {山名}"` で確認し、義務かどうか・提出先（[コンパス](http://www.mt-compass.com/)、県のフォーム、登山口のポスト）を書く。義務でなくても提出を勧める。
2. **アクセス**:
   - マイカー規制（上高地、乗鞍、立山、南アルプス林道〈北沢峠〉、尾瀬、富士山 など）: `WebSearch "{山名} マイカー規制 {今年}"`
   - 登山バス・路線バスの季節運行と時刻表: `WebSearch "{登山口} バス 時刻表 {今年}"`（運行期間・始発時刻・予約制か）
   - 林道・道路の通行止め、冬季閉鎖: `WebSearch "{林道名 or 道路名} 通行止め {今年}"`、各県の道路規制情報、[JARTIC](https://www.jartic.or.jp/)
   - 登山口の駐車場（台数・料金・満車になる時刻）
3. **入山料・協力金・予約**: 富士山の通行料・事前予約、尾瀬・屋久島などの協力金、山小屋・テント場の予約制。金額や制度は毎年変わるので必ず今年の情報を検索する。
4. **火山**: `volcano.is_volcanic_area` が true、または Wikipedia で活火山とされている場合、`WebSearch "{火山名} 噴火警戒レベル site:jma.go.jp"` で現在のレベルと立入規制範囲を確認する。[気象庁 火山登山者向けの情報](https://www.data.jma.go.jp/vois/data/tokyo/STOCK/activity_info/index.html)も参照。
5. **熊**: `WebSearch "{都道府県} クマ 出没情報 {今年}"`、`"{市町村} クマ 目撃 {山名}"`。北海道はヒグマ。出没が多い年・地域は注意喚起の内容と日付を書く。
6. **緊急連絡**: 管轄の警察署（`police` の結果）と、都道府県警の山岳遭難救助の窓口。

まとめ方の例:
> 「アクセス（{調査日}時点）: 沢渡〜上高地はマイカー規制中のため、沢渡駐車場からシャトルバス・タクシー（[松本市](url)）。」

### フェーズ4: ルート分析

#### 4A: ルートの種類

- **一般登山道**: 整備された登山道。鎖場があっても短い
- **岩稜・鎖場**: 鎖・梯子の連続、痩せ尾根、三点支持が必要（例: 剱岳別山尾根、大キレット）
- **雪山**: 積雪・凍結。アイゼン・ピッケル必須
- **バリエーション**: 登山道ではないルート。ロープ・確保技術が必要なことがある
- **沢登り**: 遡行図・グレード（1級〜）で表す

#### 4B: 情報の統合

**優先順位:** 1. 山小屋・自治体の最新のお知らせ　2. 直近の山行記録　3. ガイドブック・公式のコース情報　4. スクリプトの計算値

1. 公式・ガイドの情報（ルート名、グレーディング、コースタイム）を土台にする
2. 山行記録から目印・実際のタイム・状況を足す
3. 情報が食い違うときは両方書く（「公式は通行可、9月の記録では一部崩落で迂回」など）
4. 複数の記録が一致することは「複数の記録で〜」とまとめる
5. 場所・標高・時刻など具体的に
6. **特定の記録に基づく記述は、必ずその記録へのリンクにする。**「[2026年9月の記録](url)では〜」のように書き、地の文で「ある記録では」とだけ書かない。まとめて言う場合も2〜3件にリンクする。

**危険箇所は種類ごとに分けて書く（「危険」の一言にまとめない）:**

- **落石**: 場所、原因（他パーティ・融解・雨）、対策（ヘルメット、通過は素早く・間隔を空ける、時間帯）
- **滑落・転落**: 鎖場・梯子・痩せ尾根・ガレ場・凍結箇所、落ちたらどうなるか
- **道迷い**: 分岐、踏み跡が多い所、ガスで迷いやすい所（日本の山岳遭難の原因で最も多い）
- **雪渓・雪庇・雪崩**: 場所、時期、避け方
- **天候**: 夏の午後の雷、強風の稜線、低体温症
- **火山**: 噴火警戒レベル、火山ガス、規制範囲
- **生き物**: 熊、スズメバチ、ヤマビル、マムシ
- **渡渉・増水**: 沢の場所、雨のあとの増水
- **エスケープルート**: どこから、どの条件で下りるか

**主な数値:**

- 難易度（グレーディングがあればそれ、なければ根拠を示して推定）
- 核心部
- 登山口と主なコース
- 距離・累積標高差・コースタイム（ガイド値と実測値を比較）
- 歩行時間とコース定数: `time_estimates` を使う。無ければ距離・標高差が分かった時点で `fetch_conditions.py` を `--distance-km --up-m` 付きで再実行。出発時刻が分かれば `--start-time`、通過点があれば `--waypoint` も付ける
- **0℃高度の注意**: どの日かの 0℃高度が山頂から600m以内なら「凍結・降雪の可能性」として注意を書く。ずっと山頂より600m以上高ければ省く

#### 4C: 地図リンク

**レポートに出てくる地名には必ず地図リンクを付ける。** 座標があれば:

- 地理院地図: `https://maps.gsi.go.jp/#15/{緯度}/{経度}/`
- Google マップ: `https://www.google.com/maps/search/?api=1&query={緯度},{経度}`

名前しか分からない場所（記録に出てくるテント場など）は Google マップの名前検索 `https://www.google.com/maps/search/?api=1&query={URLエンコードした名前+都道府県}`。見つからなければそう書く。

病院・警察・山小屋は、公式サイトがあればそこへ、なければ Google マップの名前＋住所検索へリンクする（座標だけのリンクにしない）。電話番号・住所が OSM に無ければ、公式サイトなどで調べて埋める。

#### 4D: 不明点の整理

取れなかったもの・確かでないものを書き出す（記録が少ない、季節の記録がない、スクリプトの失敗、情報の食い違い、古い情報しかない）。

### フェーズ6: レビュー

```

  subagent_type="general-purpose",
  model="opus",
  prompt="""あなたは日本の山のルート調査レポートのレビュアーです。

1. レポートを読む: {report_file_path}
2. 確認する:
   - 事実の一貫性: 日付と曜日が合っているか、標高・距離・時刻が全体で矛盾しないか、0℃高度と降水の種類（雨/雪）が整合するか
   - 計算: 標高差・コースタイム・単位

   - 完全性: {プレースホルダ} が残っていないか、必須の節（概要・ルート・アクセス・現在の状況・山行記録・不明点・情報源）があるか
   - 安全: AI 生成の注意書きがあるか、噴火警戒レベル・警報・熊の注意が必要な場合に書かれているか、登山届の記述があるか

   - 軽微（書式）: すぐ直せるなら直す

### フェーズ7: 完了報告

1. 「{山名}のルート調査が終わりました」
2. レポートのファイルパス
3. 2〜3文の要約（ルートの種類と難易度、主な危険と注意、大きな不明点）
4. 次の一歩:
   - 出発前日〜当日に天気・警報・山小屋のお知らせを見直す
   - 登山届を出す（[コンパス](http://www.mt-compass.com/)など）
   - 行程表や方位が欲しければ `--start-time` や `--waypoint` を付けて再実行できる。`after_dark` / `late_arrival` が true なら目立つように伝える
   - 下山後、`{skill_dir}/assets/trip-report-template.md` を使って山行記録を残せる

```

## エラー時の方針

- **止めない**: スクリプトやエージェントが失敗しても、不明点に書いて続ける
- **代わりの手段を示す**: 手動で確認するリンク（気象庁、tenki.jp 山の天気、てんきとくらす など）を載せる
- **再試行は1回**: ネットワークのタイムアウトは1回だけやり直す
- **推測で埋めない**: 分からない値は「不明」と書く
- **安全情報の欠落は強調する**: 警報・火山・雪崩・熊の情報が取れなかったら、不明点の節で目立たせる

### 取得のはしご

WebFetch → `cloudscrape.py "{url}"`（速い）→ `cloudscrape.py --render "{url}"`（ブラウザで描画）→ ディスプレイがあれば `--render --headed`。すべて失敗したら不明点に書く。

## 所要時間の目安

- スクリプト: 30〜90秒（Overpass が混んでいると長くなる）
- 全体: 3〜6分、詳しい調査で最大10分程度

## 品質の原則

1. ✅ 冒頭に安全上の注意書き
2. ✅ 不明点をはっきり書く
3. ✅ 出典にリンク
4. ✅ ファイル名と本文に調査日
5. ✅ テンプレートの構成に従う
6. ✅ 行動に使える情報（距離・時間・装備・時刻）
7. ✅ 「最終判断は自分で」を強調する
