# 設計メモ

元プロジェクト（claude-mountaineering-skills の route-researcher）と同じ「決まった計算・API は Python、判断が要る調査は LLM エージェント」という分担を保ち、日本の情報源に置き換えています。

## 構成

```
skills/yama-route-researcher/
├── SKILL.md                     # ワークフロー本体（7フェーズ）
├── assets/
│   ├── report-template.md       # レポートの雛形
│   └── trip-report-template.md  # 下山後の山行記録の雛形
├── tools/
│   ├── jp_geo.py                # 地理院・気象庁地域コード・OSM の共通処理
│   ├── find_peak.py             # 山の特定
│   ├── fetch_conditions.py      # コンディション一括取得
│   ├── cloudscrape.py           # 取得しにくいページ（元プロジェクトのまま）
│   └── test_*.py
└── docs/architecture.md
```

## 日本向けにした判断

- **PeakBagger をやめた:** 日本の山の収録が薄く、同名山の区別もしにくい。OSM の山頂と地理院の地名検索を突き合わせ、市町村と標高を付けて候補を示す方が確実。
- **同名山の確認を必須にした:** 駒ヶ岳・丸山・愛宕山など、日本は同名の山が非常に多い。
- **気象庁の警報を市町村単位で:** 地理院の逆ジオコーダで市区町村コードを得て、気象庁の `area.json` で class20 → class10 → 府県予報区をたどる。都府県単位の代用値も持つ。
- **稜線の風:** Open-Meteo の10m風速は稜線で過小評価になりやすいので、山頂標高に近い気圧面（850/700hPa）の風も取る。
- **火山:** 噴火警戒レベルの機械可読な公開 API が無いので、OSM で近接火山を検出し、レベルは気象庁のページを WebSearch で確認する手順にした。
- **アクセス:** 日本の山は公共交通・マイカー規制・季節運行バス・登山届の条例が計画を大きく左右するため、3D をその調査に充てた。
- **時間の目安:** 北米の Naismith 系をやめ、日本のコースタイムに近い DIN 33466 と、日本で広く使われるコース定数にした。
- **早出早着:** 日本の山の慣習（15時ごろまでに山小屋・登山口に着く）を行程表の判定に入れた。

## 失敗時の扱い

どの取得も失敗したら `gaps` に理由を残して続ける。レポートの「不明点」に必ず載せ、安全情報（警報・火山・雪崩・熊）が欠けた場合は強調する。
